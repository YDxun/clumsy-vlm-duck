# 全流程校验与优化报告 · 2026-09-15（第二轮）

> 本轮：预算/Home 打通、物体交互补齐、Web 端改造、三场景基准复跑。
> 分支 `codex/duck-vlm-harness`。所有结论均来自服务器实测（Qwen3-VL zero-shot + MuJoCo 真值判定）。

## 1. 本轮代码改动

### 1.1 局部搜索：以最后目击点为中心（①）
`plugins.py` · `ExplorePlugin`：
- 目标可见时记录**鸭子自身位置**（里程计，不是目标真值）为 `_last_seen_xy`。
- 目击保持期（8 步）结束后，若已离开该点 `>0.35 m`，进入 SEARCH 模式：
  先转回并走回该点，再**原地扫视 4 步**，然后才恢复门洞优先巡游。
- `SUBTASK` 会 verbalize：`SEARCH: the goal was last seen near (x,y); go back there ...`
  或 `SEARCH: you are back where the goal was last seen. Sweep ... use LOOK_DOWN / LOOK_DOWN_MORE`。

### 1.2 小步接近纳入低延迟层（②）
`plugins.py` · `PluginSuite.reactive_directive`：
- 新增 `APPROACH_TASKS = (walk_to_ball, come_to_owner, go_to_beacon, search_ball_across_rooms, rough_ground_walk)`。
- 这些任务在目标可见时**完全不走 VLM 往返**：
  - `range ≥ 0.45 m`：正对 → `FWD`，偏轴 → 朝正确方向 `TURN`；
  - `0.20 ≤ range < 0.45 m` 且 `|bearing| < 0.30`：小步 `FWD`。
- ⚠️ **这是本轮修掉的一个自查回归**：第一版对**所有**任务生效，把姿态任务
  `walk_turn_stop` 的转向需求覆盖成了"朝球前进"，导致它第二轮超时（32 步 FAIL）。
  现已限定在 `APPROACH_TASKS`，并补了回归测试。

### 1.3 第二档低头（⑤）
`actions.py`：新增 `LOOK_DOWN_MORE`（`head_pitch +1.00 rad`）。
可见区间实测：`+0.60` 覆盖 0.15~0.45 m，`+1.00` 覆盖 0.10~0.22 m，
两档叠加后**只剩 <0.10 m 不可见**。别名 `LOOK_DOWN_DEEP / DEEP_LOOK_DOWN / 更深低头`，
Web 端也加了按钮，prompt 里说明了适用范围。

### 1.4 踢球站位插件（④）
`plugins.py` · `KickStationPlugin`（新，可单独消融）：
- 任务→(物体, 区域) 映射：`kick_ball_to_zone / retrieve_ball / push_ball_around_obstacle → (ball, zone_green)`，
  `push_red_cube → (obj_cube_red, zone_blue)`。
- 站位点 = **物体位置 − 指向区域的方向 × 0.28 m**（站在球的"远区侧"）。
  物体位置只在**可见时**使用（感知门控保证），区域中心来自静态元数据。
- 直线会推错方向时（鸭子已在区域侧），先绕一个 0.45 m 侧向点。
- 到达站位后细调到 `|误差|<0.22 rad`，然后**交还模型决定用哪只脚踢**。
- 子目标 verbalize：`KICK STATION: stand behind the object on the far side from the zone, at (x,y) ...`

### 1.5 Web 端
- **任务下拉**：`fillTasks()` 从 `/api/scenes` 取当前场景的 task id 填进 `<select id="task-pick">`，
  选中即写入 `#task`，避免"手打文本对不上就没有评分"。自由文本仍可用，但会标注"unscored"。
- **场景热重载**：`/api/scenes/select` 不再 `subprocess` 重启进程，改为 `Server.reload_scene()`：
  重建 `LocalSim` / `MjData` / 渲染器（Renderer 持有旧模型与 EGL 上下文，需在渲染线程 `close()`）/
  VLM 与 agent host；**保留** `PolicyBank`（ONNX 与会话不依赖模型）。
  前端切换后不再 `location.reload()` + 9 s 等待。
  实测切换耗时：**0.14 ~ 0.17 s**（原约 9 s，约 55×），切换后头摄/主视角截图正常。

### 1.6 基准方法论修复：按 `robot_spawn` 重置
`state.py` · `reset_to_spawn()` + `loop.py` 的 `spawn_setter` 钩子 + `host.py` 接线：
每个任务开始时按 `tasks.yaml` 的 `robot_spawn`（含 `random_xy_radius_m` / `random_yaw_deg`）
放置机器人。**此前连续任务会继承上一个任务的结束位姿**——`walk_turn_stop` 曾在第一轮
"3 步通过"，就是因为上一任务结束时鸭子已经站在目标区附近。修正后该结论作废，
重新测量为 11 步通过。

### 2.1 多次运行的稳定性
`search_ball_across_rooms` 共测 3 次：**PASS(78) / PASS(27) / FAIL(76)** → 2/3，
属于**临界成功**，不是稳定通过。这是本轮最值得注意的结论：
局部搜索+小步低延迟把它从"从不成功"推到"多半能成"，但仍在 60 s 预算边缘。

### 2.2 ⚠️ `recover_after_fall` 是平凡通过，不算能力
其成功条件为：
```yaml
success: all
  - upright >= 0.75
  - speed <= 0.1
  - hold_condition_s: 2.0
```
**没有任何"必须先摔倒"的前置条件**，所以鸭子原地站 2 秒就通过（实测 1 步）。
这是场景包的任务定义缺陷，不是恢复能力。建议加入
`fallen_for_s ≥ 0.5s` 的"先摔倒"前置条件（需要 Agent 自己摔或随机扰动），
否则该任务应从成功率表中剔除或标注为无效。

### 2.3 `max_duration_s` 预算放宽的处理
本轮**没有**修改场景包的 `max_duration_s`（未获授权改动已验收的场景包）。
代之以"扩大低延迟层覆盖"，把原本被 VLM 往返吃掉的预算抢回来：
- `search_ball_across_rooms` 的决策来源约 82~92 步为 `reactive`、7~16 步为 `vlm`；
- 步数上限从 32 提升到 63~109。
如需彻底通过 Home，仍建议把该任务预算 60 → 90 s（需重跑 `validate.py`）。

# 第三轮（同日）：预算、任务定义与 demo 重录

## A. Home 预算 60 → 90 s
`duck_scenes/scenes/duck_home_v1/tasks.yaml`：`search_ball_across_rooms` 的
`max_duration_s` 由 60 改为 **90**。改后已复跑 `validate.py`：**Validation: PASS**。

**但放宽预算并没有让它通过。** 90 s 下实测 107 / 140 / 105 步仍然 timeout，
说明瓶颈不是时间，而是丢球后的搜索行为（见 C）。

## B. `recover_after_fall` 任务定义修正
原成功条件只有 `upright≥0.75 + speed≤0.1 + 保持2s`，**没有"必须先摔倒"**，
鸭子原地站 2 秒即通过（实测 1 步），是无效任务。

- `validation_core.py` 新增锁存条件 **`ever_fallen`**：一旦观测到 `upright < max_upright`
  就永久置真（存在 `timers` 字典里，键 `("everfell", id(node))`，与 `fallen_for_s` 不冲突）。
- `duck_obstacle_v1/tasks.yaml` 的 `recover_after_fall` 加入该条件作为前置：
  ```yaml
  success:
    all:
      - type: ever_fallen      # 必须先真的摔倒
        body: trunk_base
        max_upright: 0.5
      - type: upright          # 再站起来
      - type: speed_xy_le
      - type: hold_condition_s: 2.0
  ```
- 已复跑 `validate.py`：**Validation: PASS**。

⚠️ **副作用（诚实说明）**：现在如果鸭子全程不摔，该任务必然超时失败。
而场景包内的 ONNX 策略只有 `alpha_stand / alpha_walking / ball_kick_* / alpha_sitstand /
alpha_ground_pick / happy_hop / roller / roller_crouch / roulade`，**没有任何"从倒地起身"的策略**，
因此当前条件下该任务**无法通过**。这是正确暴露出的能力缺口，不是回归——
要让它可解，需要训练/引入一个 stand-up 策略并加一个 `STAND_UP` 技能 token。
在此之前建议把它从成功率表中剔除。

## C. 丢球后的搜索行为修复（两个改动）
用 90 s 那次失败逐帧定位 → 鸭子已进东屋、逼近到 **1.15 m**，随后丢球；
局部搜索扫 4 步未果后**巡游恢复并把鸭子带回西屋**（1.15 m → 3.19 m）。做了两处修改：

1. **局部搜索失败后就近重入巡游**：`ExplorePlugin._resync_near()` —— 扫视失败时把巡游指针
   移到"离最后目击点最近的剩余航点"，而不是continue 原顺序（原顺序的下一格可能在另一个房间）。
2. **朝向迟滞**：`reactive_directive` 原先在 bearing ≈ 0.35 rad 阈值附近来回
   `TURN_L/TURN_R`（实测 88 个 reactive 步里大多数在转向、几乎不前进）。改为
   一旦在走就容忍到 0.60 rad 才转、一旦在转就要收到 0.22 rad 才恢复走。

**效果**：丢球后不再被带回西屋；但 Home 仍然未通过（见下表），
最深一次逼近到 **1.15 m**。

## F. 结论与下一步
1. **Home 的瓶颈已从"时间预算"变为"丢球后重获目标"**：预算翻倍无效，需要
   ①在最后目击点附近做更深的搜索（配合 `LOOK_DOWN_MORE`），或
   ②让 VLM 在目击保持期（8 步）内真正用上低头动作——实测这 8 步它只换来 7 次 VLM 决策。
2. `recover_after_fall` 需要 stand-up 策略才能作为有效指标；建议先剔除或标为 N/A。
3. 单元测试 48 项全绿；三套场景 `validate.py` 全部 PASS。
