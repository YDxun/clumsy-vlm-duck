# DuckVLM 仿真环境生成提示词

> 将下面整段内容复制给你的助手。目标是生成可直接接入 MicroDuck MuJoCo / RoboGo 仿真和 DuckVLM 闭环的场景资产，不要只给概念说明或局部 XML 片段。

---

# 任务背景

你是 MuJoCo 场景与具身智能评测环境工程师。请为 **MicroDuck 双足机器鸭**设计可运行的 MJCF 仿真场景和机器可读任务规范。

MicroDuck 的大致规格：

- 高度约 25 cm，质量约 800 g。
- 双足行走，14 个受控关节，另有头部姿态控制。
- 没有机械臂、没有多指夹爪。
- 可以执行：前进、后退、横移、原地转向、站立、用脚踢球、翻滚、跳动。
- 只能执行地面级或低矮平台任务，不能操作正常高度的 75 cm 桌面，不能抓取或叠衣服。

目标不是复刻机械臂操作，而是生成适合鸭子完成的任务：

- 走到目标附近。
- 找到正确物体。
- 追逐、接近和踢球。
- 用脚或头部推动低矮物体。
- 绕过障碍、通过门洞、走坡道。
- 跟随主人、绕开陌生人。
- 根据自然语言选择正确目标。
- 在完成条件满足后停止。

# 一、技术格式要求

## 1. 坐标系和单位

- 单位：米、千克、秒、弧度。
- 坐标：右手系，Z 轴向上。
- 地面：`z=0`。
- 默认鸭子出生点：`(0, 0, 机器人自带初始化高度)`。
- 默认头部朝向：`+X`。
- 所有物体位置均为世界坐标。

## 2. MJCF 场景格式

每个场景必须提供一个完整的 `scene.xml`，并默认通过相对路径包含机器人模型：

```xml
<include file="robot_allcollisions.xml"/>
```

如果助手本地没有该文件，可以保留相对路径占位，但必须在 README 中说明。不要使用绝对路径。

场景应包含：

- 地板。
- 光照。
- 明确的 `worldbody`。
- 命名唯一的刚体。
- 可选的静态相机。
- 任务物体。
- 目标区域或信标。
- 不修改机器人本体 XML。
- 不依赖网络纹理、外部服务器或运行时下载。

推荐基础结构：

```xml
<mujoco model="duck_workspace_v1">
  <compiler angle="radian"/>
  <include file="robot_allcollisions.xml"/>
  <option timestep="0.005"/>
  <visual>
    <headlight diffuse="0.8 0.8 0.85" ambient="0.45 0.5 0.6"/>
    <rgba haze="0.04 0.05 0.08 1"/>
  </visual>
  <worldbody>
    <light pos="2 2 3" dir="-0.5 -0.4 -1" directional="true"/>
    <geom name="floor" type="plane" size="0 0 0.05" rgba="0.12 0.14 0.18 1"/>
  </worldbody>
</mujoco>
```

## 3. 几何和物理限制

- 优先使用 `plane`、`box`、`sphere`、`cylinder`、`capsule`。
- 自定义网格尽量少于 1000 三角面。
- 单个场景资产总量建议小于 50 MB。
- 不使用布料、流体、软体、绳索、复杂柔性接触。
- 避免薄片、超小接触面、尖锐碰撞体和穿透风险。
- 物体尺寸建议 3–15 cm。
- 低平台高度建议 3–10 cm。
- 门宽建议至少 0.45 m。
- 通道宽度建议至少 0.40 m。
- 矮墙高度建议 0.15–0.30 m。
- 斜坡角度建议不超过 15–20 度。
- 地面和物体接触应稳定，连续运行 10 秒不能出现抖动、飘移或 NaN。
- 球的默认参考参数：直径 70 mm，质量 15 g，摩擦约 `0.8 0.02 0.03`。
- 可推动方块建议质量 30–100 g。
- 目标区域和信标应设置 `contype="0" conaffinity="0"`，只用于视觉和几何判定。

## 4. 命名规范

所有实体必须有稳定、唯一、语义清晰的名称：

```text
floor
wall_*
obstacle_*
obj_ball_red
obj_ball_blue
obj_cube_red
obj_cube_blue
obj_cup_green
zone_green
zone_red
beacon_target
button_low_red
door_left
door_right
person_owner
person_stranger
cam_overhead
cam_rear
cam_workspace
```

如果场景用于 DuckVLM，至少保留一个主球体并优先命名为：

```text
ball
```

附加彩色球或干扰物使用其他名称，并在 metadata 中提供语义标签。

## 5. 相机要求

每个场景至少提供：

- `cam_overhead`：固定俯视相机，用于调试和人工查看。
- `cam_workspace`：固定斜视角，展示整个工作空间。

可选：

- `cam_rear`：从鸭子后方观察。
- `cam_target`：对准目标区域。

固定相机要求：

- 不遮挡鸭子。
- 视野包含主要物体和目标区域。
- 分辨率约定 640×480 或 320×240。
- 使用稳定的相机位置和朝向，不要让相机跟随任务物体。
- 如果需要推荐参数，给出 `pos`、`xyaxes` 或 `quat`、`fovy`。

DuckVLM 的实际第一视角由现有系统根据鸭子头部姿态渲染，不要求场景额外添加鸭子头摄。

# 二、输出文件要求

每个场景输出一个独立目录，例如：

```text
scenes/duck_workspace_v1/
├── scene.xml
├── metadata.yaml
├── tasks.yaml
├── README.md
├── validate.py
├── meshes/                 # 仅自定义网格时存在
└── previews/
    ├── overhead.png
    └── workspace.png
```

## `metadata.yaml`

描述场景和实体，不要只写自然语言。至少包含：

```yaml
scene_id: duck_workspace_v1
version: 1
units:
  length: m
  angle: rad
  mass: kg
coordinate_frame:
  up: +Z
  robot_default_forward: +X
robot:
  body_name: trunk_base
  nominal_height_m: 0.25
  footprint_radius_m: 0.15
objects:
  - id: ball_red
    body: obj_ball_red
    kind: sphere
    radius_m: 0.035
    mass_kg: 0.015
    semantic_labels: [red ball, 红球, ball]
    affordances: [approach, kick, push]
    default_pose: [1.2, 0.0, 0.035]
  - id: cube_blue
    body: obj_cube_blue
    kind: box
    half_size_m: [0.035, 0.035, 0.035]
    mass_kg: 0.06
    semantic_labels: [blue cube, 蓝色方块]
    affordances: [approach, push, avoid]
    default_pose: [0.8, 0.7, 0.035]
zones:
  - id: green_zone
    body: zone_green
    radius_m: 0.35
    center: [1.5, -0.8, 0.003]
    semantic_labels: [green target zone, 绿色区域]
cameras:
  - name: cam_overhead
    resolution: [640, 480]
```

## `tasks.yaml`

任务是机器可执行、可自动判定的，不要只写“成功即可”。推荐格式：

```yaml
tasks:
  - id: kick_red_ball_to_green_zone
    instruction_zh: 找到红球并把球踢进绿色区域
    instruction_en: Find the red ball and kick it into the green zone.
    max_duration_s: 45
    success_hold_s: 0.5
    setup:
      obj_ball_red:
        xy: [0.9, 0.0]
        yaw_deg: 0
        random_xy_radius_m: 0.15
      zone_green:
        center: [1.5, -0.8]
    success:
      all:
        - type: body_in_zone
          body: obj_ball_red
          zone: zone_green
          radius_m: 0.20
        - type: upright
          body: trunk_base
          min_upright: 0.55
    failure:
      any:
        - type: outside_bounds
          radius_m: 2.5
        - type: fallen_for_s
          seconds: 5.0
```

必须明确：

- 机器人出生位置和朝向范围。
- 目标物、干扰物、区域的位置。
- 允许的随机化范围。
- 成功条件。
- 失败条件。
- 最大时长。
- 成功条件需要保持的时长。
- 哪些物体是静态，哪些是自由刚体。
- 任务是否可以重新开始。

# 三、需要优先生成的场景

## 场景 A：`duck_workspace_v1`

第一优先级，用于 VLM 目标选择、接近、踢球和推物。

场地：

- 4 m × 4 m 平面。
- 10 cm 高矮墙围住工作区。
- 一个 1.5 m × 1.0 m、高 6 cm 的低平台。
- 一个固定俯视相机和一个固定斜视相机。

物体：

- `ball`：橙色足球，直径 70 mm，质量 15 g。
- `obj_ball_blue`：蓝色球，直径 60 mm，质量 12 g，作为干扰物。
- `obj_cube_red`：红色方块，边长 6 cm，质量 50 g。
- `obj_cube_blue`：蓝色方块，边长 6 cm，质量 50 g。
- `obj_cup_green`：绿色矮圆柱，半径 3 cm，高 7 cm，质量 30 g。
- `zone_green`：半径 35 cm 的绿色目标区域。
- `beacon_target`：高 40 cm、无碰撞的信标。

推荐任务：

1. `walk_to_ball`：走到球附近 40 cm 内并停住。
2. `kick_ball_to_zone`：找到橙色球并踢进绿色区域。
3. `push_red_cube`：把红方块推到蓝色区域。
4. `choose_red_not_blue`：在两个方块中选择红方块。
5. `walk_turn_stop`：向前走，右转，然后停止。
6. `avoid_obstacle_reach_beacon`：绕过两个障碍物到达信标。

## 场景 B：`duck_home_v1`

用于语义导航、认人和跨房间搜索。

场地：

- 6 m × 5 m。
- 两个房间，一个门洞，门宽至少 0.5 m。
- 矮墙高度 25 cm。
- 低矮沙发，高 10 cm。
- 低矮茶几，高 8 cm。
- 门框、墙体和家具全部使用稳定碰撞体。

人物：

- `person_owner`：红色躯干，作为主人 proxy。
- `person_stranger`：蓝色躯干，作为陌生人 proxy。
- 人物可以是静态、mocap 或 kinematic body，但必须声明类型。
- 不要求人脸识别，只需要支持语义标签和位置真值。

任务：

1. `come_to_owner`：找到主人并靠近。
2. `follow_owner`：保持 0.5–1.0 m 跟随距离。
3. `orbit_stranger`：陌生人靠近时绕到侧后方。
4. `search_ball_across_rooms`：穿过房间找到球。
5. `go_to_beacon`：根据语义目标前往信标。
6. `retrieve_ball`：找到球并把它带到指定区域，允许使用踢/推而不是抓取。

## 场景 C：`duck_obstacle_v1`

用于摔倒恢复、路径重规划和鲁棒性评估。

场地：

- 5 m × 4 m。
- 低台阶：5 cm、10 cm。
- 坡道：10–15 度。
- 窄通道：40–60 cm。
- 可移动箱子和固定柱子。
- 地面可增加少量低摩擦/高摩擦区域，但必须稳定。

任务：

1. `rough_ground_walk`：通过坡道和台阶到达目标。
2. `narrow_corridor`：通过 0.5 m 宽通道。
3. `recover_after_fall`：摔倒后恢复站立。
4. `push_ball_around_obstacle`：带球绕过障碍。
5. `multi_target_navigation`：按顺序访问红色、蓝色和绿色区域。

# 四、适合鸭子的任务设计原则

允许：

- 地面级物体。
- 低平台。
- 踢、推、顶、踩按钮。
- 转向、接近、搜索、跟随。
- 低矮门洞和通道。
- 两到三个目标的语义选择。
- 需要失败恢复的长程任务。

不要优先设计：

- 抓取。
- 多指手操作。
- 叠衣服。
- 拧瓶盖。
- 正常高度桌面任务。
- 超过鸭子身高 2 倍的平台。
- 要求精细毫米级插入的任务。
- 依赖视觉之外的外部状态注入才能成功的任务。

# 五、验证要求

助手必须实际验证并报告：

1. XML 能被 MuJoCo 成功加载。
2. 运行至少 1000 个 `mj_step` 不出现 NaN。
3. 所有自由物体没有初始穿透。
4. 所有命名在场景内唯一。
5. 所有任务引用的 body/zone 都存在。
6. 成功条件可以在 1–3 分钟内人工复核。
7. 提供至少两张预览图：`cam_overhead` 和 `cam_workspace`。
8. 提供加载命令和验证命令。
9. 如果自定义了网格，附上网格来源和许可证。
10. 如果使用了人物 proxy，说明其运动方式和碰撞设置。

推荐验证命令：

```bash
python -c "import mujoco; m=mujoco.MjModel.from_xml_path('scene.xml'); print('nbody',m.nbody,'ngeom',m.ngeom)"
python validate.py scene.xml
```

请直接输出完整文件树和每个文件的完整内容，不要只给设计说明。按以下顺序组织：

1. 场景目标。
2. 文件树。

1. `duck_workspace_v1`
2. `duck_home_v1`
3. `duck_obstacle_v1`
